# CK3 Helper — дизайн первой версии

Дата: 2026-11-17. Статус: согласовано с владельцем (раунды Q1–Q17), исправлено по независимому
ревью. Решения для приложения (план 2) — Q18–Q32, раунд 2026-11-17; §4.8 расписан по ним.

## 1. Зачем

Игроки с большими плейсетами (десятки–сотни модов) не видят, какие моды друг друга
перезаписывают и почему. Paradox Launcher порядок не сортирует и конфликты не показывает;
Irony Mod Manager для CK3 управляет модами, но поиска конфликтов для CK3 не имеет
(в их таблице игр: Conflict Solver — No). Единственная попытка сделать сортировщик для CK3
(ck3oop) заброшена в июне 2025.

CK3 Helper v1 отвечает на два вопроса:
1. **Кто кого перезаписал** — карта конфликтов между модами плейсета с объяснением,
   почему победил именно этот вариант.
2. **В каком порядке поставить моды** — предложение порядка «сейчас → предлагаем»
   с причиной каждого перемещения и списком конфликтов, у которых сменится победитель.

Важное ограничение, которое программа говорит пользователю прямо: порядок в плейсете решает
только конфликты **одинаковых файлов** и действие `replace_path`. Победителя среди объектов и
ключей локализации из файлов с разными именами решают имена файлов, а не порядок — там
программа советует compatch, а не перестановку.

## 3. Объём

**Входит в v1:** чтение плейсетов из лаунчера; индекс модов; карта конфликтов трёх уровней;
опционально — сравнение с ванилью (включая папки DLC); предложение порядка; создание
отсортированной копии плейсета; сверка прогноза с `database_conflicts.log`; CLI `ck3h`;
десктоп-приложение.

**Не входит в v1:** разбор `error.log`, ck3-tiger, проверка после патча, переводчик,
Paradox Mods, объектный анализ GUI, `on_action`, `defines`, `genes` и баз-«контейнеров»
(§4.2), события по ID, изменение существующих плейсетов, включение/выключение и подписка на
моды, автообновление (в v1 — только проверка, есть ли новая версия), упакованные в архив DLC,
ручная перестановка модов в приложении, автораспознавание модов-переводов, отмена идущего анализа.

## 4. Архитектура

```
ck3-helper/
  crates/ck3h-core/   библиотека: всё, что знает про CK3 (без UI, без сети)
  crates/ck3h-cli/    бинарник `ck3h`: для разработки, проверки и продвинутых игроков
  app/                Tauri v2 + React + TypeScript (план 2)
    src-tauri/        крейт `ck3h-app`: состояние, команды, файлы настроек, проверка обновлений
    src/              интерфейс: экраны, локализация интерфейса
```

- **План 1** — `ck3h-core` + `ck3h-cli`: рабочий, тестируемый инструмент в терминале.
- **План 2** — приложение Tauri поверх готового ядра (экраны, локализация интерфейса,
  настройки, сборки под Windows/macOS/Linux, проверка обновлений).

### 4.1 Источники данных

| Что | Откуда |
|---|---|
| Папка пользователя Paradox | Windows: `Documents\Paradox Interactive\Crusader Kings III` (системная папка «Документы», с учётом OneDrive); macOS: `~/Documents/Paradox Interactive/Crusader Kings III`; Linux: `~/.local/share/Paradox Interactive/Crusader Kings III`. Переопределяется |
| Плейсеты и порядок | `launcher-v2.sqlite`: `playsets` (id, name, isActive, isRemoved), `playsets_mods` (playsetId, modId, enabled, position), `mods` (id, displayName, steamId, source, dirPath). Удалённые плейсеты (`isRemoved = 1`) не показываются |
| Метаданные мода | `descriptor.mod` в папке мода: `name`, `version`, `supported_version`, `dependencies` (по **именам**), `replace_path`, `remote_file_id` |
| Язык игры | `pdx_settings.txt` → `"language"={ value="l_russian" }`; переопределяется |
| Что реально запускалось | `dlc_load.json` → `enabled_mods`: список `mod/<имя>.mod` последнего запуска |
| Ваниль (опционально) | папка `game/` установки (без `game/dlc/`), затем каждая `game/dlc/<папка>/` как следующий слой. Не найдена — переключатель «ваниль» недоступен |
| Правда движка | `logs/database_conflicts.log`: `Overriding entry '<key>' for database '<db>' in 'file: <path> line: <n>'` |

Таблица `mods_dependencies` в реальной базе пуста — зависимости берём только из `descriptor.mod`.

### 4.2 Индекс мода

Для каждого мода плейсета (`dirPath` существует):

- **Файлы:** все файлы папки мода, кроме файлов в её корне (`descriptor.mod`, `thumbnail.png`,
  README и т.п.) и скрытых (сегмент пути начинается с `.`). Путь нормализуется к `/`.
  **Совпадение путей** (тот же файл) — по правилам файловой системы платформы: без учёта
  регистра на Windows и macOS, с учётом регистра на Linux. **Порядок чтения** — покомпонентный,
  по исходному написанию пути, побайтово с учётом регистра (как в tiger; подтверждено
  реальным логом: `02_all_…` ваниль читается после `02_EPE_…`, потому что 'E' < 'a').
- **Базы данных:** путь файла сопоставляется с таблицей корней баз (самый длинный подходящий
  префикс). Таблица = список CK3 `COMMON_DIRS` из ck3-tiger (164 корня, включая вложенные вроде
  `common/culture/cultures`) + корни `gfx/`, встреченные в `database_conflicts.log`:
  `gfx/portraits/portrait_animations`, `gfx/portraits/accessories`,
  `gfx/portraits/portrait_modifiers`, `gfx/portraits/trait_portrait_modifiers`,
  `gfx/portraits/cameras`, `gfx/models/units/entity_links`,
  `gfx/interface/illustrations/scripted_illustrations`, `gfx/court_scene/scene_cultures`,
  `gfx/court_scene/character_roles`, `gfx/coat_of_arms/colored_emblems`.
  Файл под `common/` без совпадения → корень `common/<первая папка>`.
  Файлы баз могут лежать в подпапках корня; база у них та же.
- **Объекты:** в каждом `.txt` файла базы — ключи верхнего уровня (`key = {…}` или
  `key = value`), кроме ключей на `@`. Разбор — крейтом `jomini`; дополнительно проверяется
  баланс фигурных скобок (вне строк и комментариев).
- **Без объектного анализа (только файловый):** `common/on_action` (списки сливаются),
  `common/defines` (слияние по ключам), `common/genes` (категории сливаются),
  `common/province_terrain` (ваниль повторяет id провинций в разных файлах, игра не считает это
  переопределением — подтверждено калибровкой), а также
  базы-«контейнеры», где верхний ключ — обёртка, а не объект: `common/named_colors`
  (`colors = {…}`), `common/coat_of_arms/coat_of_arms` (`template = {…}`),
  `common/landed_titles` (титулы вложены друг в друга).
- **Локализация:** файлы `localization/**/*.yml`, в имени которых есть `l_<язык>`.
  Анализируется один язык (язык игры или выбранный). Строка: ` ключ:N "значение"`
  (номер необязателен). Файл, в пути которого есть сегмент `replace`, — replace-файл.
- **Кодировка:** BOM убирается, UTF-8 декодируется с заменой битых байтов; файл с битыми
  байтами даёт предупреждение, но индексируется.
- Ошибка разбора или несбалансированные скобки → предупреждение, объекты файла не учитываются,
  анализ продолжается.

### 4.3 Правила движка (как определяется победитель)

Источник — исходники ck3-tiger (`src/fileset.rs`, `src/db.rs`, `src/data/localization.rs`) и
`database_conflicts.log`. Доказательства и степень уверенности — в скилле `ck3-engine-rules`.

1. **Файлы.** Слои в порядке загрузки: ваниль, DLC, моды по возрастанию `position`.
   Одинаковый относительный путь → загружается файл **последнего** слоя (мод ниже в
   плейсете); остальные копии не загружаются.
2. **`replace_path`.** Мод с `replace_path = "X"` убирает все файлы, лежащие **ровно** в папке
   `X` (не в подпапках), у ванили, DLC и всех модов **выше** него в плейсете. Применяется на
   файловом шаге, до правил 3–4.
3. **Объекты баз данных.** Учитываются только загружаемые файлы. Файлы одной базы
   упорядочиваются по пути (покомпонентно); объекты читаются в этом порядке, внутри файла —
   сверху вниз. **Побеждает последнее определение.** Поэтому `zz_a.txt` бьёт `00_b.txt`,
   даже если мод с `zz_a.txt` выше в плейсете.
4. **Локализация.** Файлы в том же порядке. Обычные файлы: **побеждает первое** определение
   ключа. replace-файл перезаписывает ключ; среди нескольких replace-файлов побеждает последний.

Правила 1 и 3 проверяются командой `ck3h calibrate` (§6); правило 4 — вручную в игре.

### 4.4 Конфликт и его пометка

Конфликт = один и тот же файл / объект (база + ключ) / ключ локализации определён в двух и
более источниках (модах; ваниль — при включённом переключателе).

- **Задумано** — мод-победитель зависит от каждого проигравшего мода, напрямую или через цепочку.
  Зависимости — из `dependencies` и из правил пользователя (§4.5): правило «A раньше B» считается
  зависимостью B от A (Q20). Правила с именем, которое не нашлось или нашлось у нескольких модов,
  не учитываются.
- **Подозрительно** — иначе.
- **Ваниль** — конфликт мода только с ванилью, в котором **победил мод** (нормальное поведение
  модов, скрыт по умолчанию). Если ваниль победила мод, правка мода в игре не действует — это
  **подозрительно**.

**Пара модов** — победитель конфликта и один из его проигравших источников (не он сам).
Конфликт с несколькими проигравшими входит в несколько пар. Пометка пары: проигравший — ваниль →
«ваниль»; победитель — ваниль → «подозрительно»; победитель зависит от проигравшего (с правилами)
→ «задумано»; иначе «подозрительно». У пары считается число конфликтов каждого уровня, в которых
она встречается. Пары упорядочены: подозрительные, задуманные, ваниль; внутри — по убыванию
числа конфликтов, затем по id победителя и проигравшего.

Compatch — мод, у которого в `dependencies` два и более мода плейсета; в отчёте он получает
метку «compatch» (на пометку конфликта не влияет). Зависимость сопоставляется с `name` из
`descriptor.mod` других модов: без учёта регистра и пробелов по краям; `steam:<id>` —
по Steam ID. Не нашлась → «отсутствует зависимость»; нашлось несколько модов с таким именем →
«неоднозначная зависимость» (ребро не строится).

### 4.5 Сортировка

Ограничения «A раньше B»:
1. зависимость раньше зависящего (если зависимость есть в плейсете);
2. правила пользователя из `rules.toml`.

Сортируются только включённые моды; **выключенные остаются на своих местах**, включённые
раскладываются по оставшимся местам. Алгоритм — устойчивая топологическая сортировка (Кан):
из доступных модов берётся тот, у кого меньше текущая позиция. Цикл → ошибка со списком модов,
образующих цикл (не всех заблокированных), предложения нет.

**Перемещение** — мод, чья позиция меняется, если (а) он участвует в ограничении, нарушенном в
текущем порядке, или (б) он связан ограничением (напрямую или по цепочке) с модом из пункта (а) и
поэтому поехал вместе с ним — например, сабмоды и compatch'и основного мода. «Поехал вместе»
значит: соседний по ограничению мод сам сдвинулся туда, куда это ограничение толкает данный мод
(тот, что должен стоять раньше, уехал позже — и данный мод тоже уехал позже; или наоборот), а
неподвижные моды движение не передают. Для него
показываются позиция «было/стало» и причины (для (б) — его собственное ограничение). Моды,
сдвинутые только потому, что переставили соседей, перемещениями не считаются.

Результат: новый порядок; перемещения; конфликты, у которых сменится победитель (анализ
прогоняется на новом порядке).

Правило «A раньше B» также означает «B намеренно перекрывает A» — конфликты, где B победил A,
помечаются задуманными (§4.4).

Формат `rules.toml` (в папке настроек приложения; общая база сообщества позже — тот же формат):

```toml
[[rule]]
before = "Medieval Arts"          # имя мода из descriptor.mod или "steam:<id>"
after = "steam:3816257844"
note = "compatch грузится после основы"
```

### 4.6 Применение порядка

1. Сама функция записи проверяет, что лаунчер закрыт (процессы по списку имён,
   настраивается); найден — отказ с понятным сообщением. Интерфейс эту проверку обойти не может.
2. Бэкап: копия `launcher-v2.sqlite` рядом, имя `launcher-v2_ck3helper_<ГГГГ-ММ-ДД_ЧЧ-ММ-СС>.sqlite`;
   файл создаётся только как новый (при совпадении имени — суффикс `_2`, `_3`…), существующий
   бэкап не перезаписывается никогда.
3. В одной транзакции: новая строка `playsets` (новый UUID, имя `<исходное> (CK3 Helper)`,
   при совпадении — `(CK3 Helper 2)` и т.д., `isActive=0`, `loadOrder='custom'`,
   `createdOn`/`updatedOn` = текущее время в мс, `syncState='NOT_ELIGIBLE'`);
   строки `playsets_mods` с новыми позициями `0..n-1` и прежними `enabled`;
   копия строк `playsets_dlcs` исходного плейсета.
4. Любая ошибка → откат; существующие строки не изменяются никогда.

### 4.7 CLI `ck3h` (план 1)

```
ck3h [--user-dir <путь>] playsets [--json]
ck3h [--user-dir <путь>] conflicts [--playset <имя>] [--lang l_russian] [--game <путь>] [--rules <файл>] [--json]
ck3h [--user-dir <путь>] sort [--playset <имя>] [--rules <файл>] [--json] [--apply]
ck3h [--user-dir <путь>] calibrate [--playset <имя>] [--game <путь>] [--json]
```
`calibrate` без ванили бессмысленна: без `--game` она ищет игру в стандартной папке Steam,
а если не находит — просит указать путь.
По умолчанию — активный плейсет. Вывод CLI — на английском; локализация — в приложении.
Позиции в выводе — с 1 (`#1` — первый мод).

### 4.8 Приложение (план 2)

**Подходы (Q18).** Рассматривались три способа связать интерфейс с ядром: (А) ядро работает в
процессе приложения, результат анализа живёт в Rust-части, интерфейс получает сводку и страницы;
(Б) весь отчёт уходит в интерфейс одним JSON, группировка и фильтры — на TypeScript; (В)
приложение запускает `ck3h --json` отдельным процессом. Выбран А: с ванилью отчёт — десятки
мегабайт, пары и их пометки должны считаться там же, где правила движка, и проверяться
Rust-тестами; (В) переиндексирует моды на каждое действие и не даёт показать прогресс.

#### 4.8.1 Устройство

- `ck3h-app` (`app/src-tauri`) — член workspace. Ядро о приложении не знает; сеть есть только в
  `ck3h-app` (проверка обновлений, §4.8.6).
- Состояние приложения: настройки; текущий анализ — загруженный плейсет, граф зависимостей,
  правила, отчёт конфликтов, пары; индекс ванили — строится один раз на папку игры и язык, при
  первом включении ванили или открытии сверки.
- Тяжёлая работа идёт в отдельном потоке; прогресс («мод 23 из 60», «индексирую игру») приходит
  в интерфейс по каналу Tauri. Пока идёт анализ, выбор плейсета и действия недоступны.
- Изменение правил не переиндексирует моды: пересчитываются только пометки и пары. Смена языка
  анализа или папки пользователя — полный повторный анализ.
- Интерфейс получает: сводку анализа (моды со статусами, счётчики по уровням и пометкам, пары),
  страницы конфликтов пары или поиска, предложение порядка, отчёт сверки. Имена модов подставляет
  Rust-часть; позиции в данных — с 0, на экране — с 1.
- Типы данных для TypeScript генерирует `ts-rs` из структур `ck3h-app` в `app/src/api/bindings/`;
  CI проверяет, что сгенерированное совпадает с закоммиченным.
- Ошибка для интерфейса — код из фиксированного списка и необязательный список строк (имена
  процессов, моды цикла, путь): нет папки пользователя, нет базы лаунчера, схема базы, плейсет не
  найден, нет активного плейсета, лаунчер запущен, список процессов недоступен, плейсет изменился,
  цикл, не папка игры, нет лога, правила не читаются, ввод-вывод, база. Текст пользователю —
  в интерфейсе на его языке; исходное сообщение ядра — в деталях.
- Доступ интерфейса к системе — только команды приложения и плагины Tauri `dialog` (выбор папки)
  и `opener` (показать файл в папке, открыть ссылку на релиз). Файлы читает только Rust-часть.

#### 4.8.2 Экраны

Боковое меню. «Конфликты», «Порядок» и «Сверка» доступны после анализа плейсета. В шапке — имя
плейсета, «Обновить» (перечитать лаунчер и пересчитать) и баннер новой версии.

1. **Плейсет.** Плейсеты лаунчера, активный отмечен; выбор запускает анализ с прогрессом. После
   анализа — сводка (модов, включено, не найдено на диске, проблемы зависимостей, compatch) и
   таблица модов со статусами: «не найден на диске», «нет зависимости X», «неоднозначная
   зависимость X», «compatch», «заменяет папку X» (`replace_path`), число предупреждений индекса
   (по клику — файлы и сообщения), «Открыть папку».
2. **Конфликты.** Переключатель «учитывать ваниль» (нужна папка игры; значение запоминается).
   Вкладка «Пары модов» (по умолчанию): строка — победитель → проигравший, числа файлов, объектов
   и строк локализации, пометка пары (§4.4); фильтр по пометкам (по умолчанию подозрительные и
   задуманные). Раскрытая пара — её конфликты страницами с объяснением. У подозрительной пары двух
   модов — кнопка «Задумано»: подтверждение («Y будет грузиться раньше X; если сейчас X выше Y,
   на экране «Порядок» появится перестановка») → правило «проигравший раньше победителя» в
   `rules.toml` (мод указан как `steam:<id>`, если он из Workshop, иначе по имени; в заметке —
   «задумано: X перекрывает Y» с именами) → пересчёт пометок. Если проигравший уже зависит от
   победителя (с учётом правил), правило создало бы цикл: кнопка недоступна, подсказка объясняет
   почему. Вкладка «Все конфликты» — плоский список с поиском по пути или ключу и фильтрами по
   уровню и пометке. Длинные списки виртуализированы.
3. **Порядок.** Предложение для плейсета: список «сейчас → предлагаем» с выделенными
   перемещениями; у перемещения — было/стало и причины («зависит от X», «нужен для X», «ваше
   правило: раньше / позже X — заметка»); конфликты, у которых сменится победитель; неприменённые
   правила. Порядок уже правильный — так и сказано, применять нечего. Цикл — ошибка со списком
   модов цикла и подсказкой, что его обычно создаёт правило против зависимости.
4. **Сверка с игрой.** Нужны папка игры и `logs/database_conflicts.log`. Итог «совпало N,
   разошлось M»; предупреждения «лог оборван» и «лог от другого набора модов» (§5); раскрываемые
   списки: расхождения, «в логе есть, у нас нет» и «у нас одно определение» по базам,
   «предсказали, а в логе нет».
5. **Настройки.** Папка пользователя CK3 и папка игры (автоопределение, выбор через диалог); язык
   анализа (по умолчанию — язык игры); язык интерфейса; проверка обновлений; имена процесса
   лаунчера (в разделе «дополнительно»); правила порядка — список с заметками, добавление (два мода
   плейсета и заметка), удаление; неприменённые правила отмечены.

При запуске приложение читает плейсеты и сразу анализирует активный; другой плейсет выбирается на
экране «Плейсет». Первый запуск без базы лаунчера в папке по умолчанию открывает «Настройки» с
объяснением.

**Объяснения** собираются интерфейсом из уровня, причины, пометки, имён и файлов:
- файл, мод ниже в плейсете: «Загружается файл мода X: он ниже в плейсете; копии остальных модов
  не загружаются»;
- объект, позже по пути: «Игра читает файлы базы по алфавиту пути и берёт последнее определение:
  `zz_a.txt` идёт после `00_b.txt`. Порядок модов тут не решает — нужен compatch»;
- локализация, раньше по пути: «Из обычных файлов локализации побеждает первое определение по
  алфавиту пути»; папка replace: «Файл из папки replace перебивает обычные»;
- ваниль победила мод: «Правка мода в игре не действует»;
- у конфликтов локализации показаны тексты всех сторон.

#### 4.8.3 Применение порядка

Кнопка «Сохранить как новый плейсет» на экране «Порядок». Пока экран открыт, приложение раз в 2 с
проверяет процессы лаунчера: найден — кнопка недоступна, «Закройте Paradox Launcher: <имена>»;
список процессов недоступен — кнопка недоступна, отдельный текст. Перед записью приложение
перечитывает моды плейсета из базы и сравнивает с проанализированными (id, позиция, включён);
различие → «Плейсет изменился в лаунчере после анализа» и предложение пересчитать. Диалог
подтверждения показывает (не даёт изменить) имя, которое получит копия по §4.6, папку бэкапа и
напоминание, что исходный плейсет не меняется; имя считает функция ядра только для чтения, общая с
`apply_order`. Запись — только
`apply_order` ядра; его проверку лаунчера интерфейс не обходит. После — имя созданного плейсета,
«Показать бэкап в папке» и подсказка выбрать новый плейсет в лаунчере.

#### 4.8.4 Файлы приложения

Папка `<config>/ck3-helper/` — общая с CLI (`~/Library/Application Support` на macOS,
`~/.config` на Linux, `%APPDATA%` на Windows):
- `rules.toml` — формат §4.5. Приложение добавляет и удаляет `[[rule]]`, сохраняя остальной текст
  и комментарии. Файл не читается → баннер с ошибкой, анализ без правил, правка правил недоступна
  до исправления файла.
- `settings.toml` — папка пользователя, папка игры, язык анализа, язык интерфейса, «учитывать
  ваниль», проверка обновлений и время последней, имена процесса лаунчера; всё необязательно.
  Не читается → значения по умолчанию и баннер; при сохранении старый файл переименовывается в
  `settings.toml.bak`.

Кроме этих двух файлов приложение пишет только через `apply_order` (база лаунчера и её бэкап).

#### 4.8.5 Языки

Интерфейс на русском и английском; по умолчанию — язык системы (`ru*` → русский, иначе
английский). Тексты — в ресурсах интерфейса, один набор ключей на оба языка (тест сверяет),
русские формы множественного числа. Язык анализа — из `pdx_settings.txt`, иначе `l_english`;
меняется в настройках. Имена модов и тексты локализации модов показываются как есть.

#### 4.8.6 Проверка обновлений

При запуске, если включена и с прошлой проверки прошло больше суток: запрос последнего релиза
репозитория проекта в GitHub Releases (таймаут 5 с, User-Agent `ck3-helper/<версия>`, без личных
данных). Версия новее текущей — баннер «Доступна версия X» со ссылкой на страницу релиза. Ошибка
сети — молча, до следующего запуска через сутки. Скачивает и ставит новую версию пользователь.

#### 4.8.7 Сборки и CI

- CI на каждый push и PR, на Windows, macOS и Linux: `cargo fmt --check`, `clippy -D warnings`,
  `cargo test --workspace --all-features`, сверка сгенерированных типов, линтер, проверка типов и
  тесты интерфейса.
- Релиз по тегу `v*` через `tauri-action`, черновиком: Windows — установщик NSIS для текущего
  пользователя (без прав администратора); macOS — universal `.dmg` (Intel и Apple Silicon) с
  ad-hoc подписью; Linux — AppImage и `.deb`. В описании релиза — инструкция запуска неподписанной
  программы на русском и английском (Windows: «Подробнее → Выполнить в любом случае»; macOS:
  «Системные настройки → Конфиденциальность и безопасность → Всё равно открыть» или
  `xattr -dr com.apple.quarantine`).
- Обе схемы заработают, когда появится репозиторий на GitHub; до этого — локальная сборка на macOS.

#### 4.8.8 Проверка приложения

- Rust: логика команд на `testkit` — анализ, пары, страницы, правка правил с сохранением
  комментариев, проверка «плейсет изменился», коды ошибок. Реальная база не используется.
- Интерфейс: Vitest + Testing Library, вызовы ядра подменены (`mockIPC`): экраны, «Задумано»,
  блокировка применения при запущенном лаунчере, объяснения, одинаковые ключи ru/en.
- Сквозных тестов через WebDriver нет: Tauri не поддерживает его на macOS.
- В конце — ручной чек-лист на реальном плейсете владельца; применение — на копии папки
  пользователя. Windows — вручную, если есть машина (Q32).

#### 4.8.9 Подготовка ядра

- Модуль `session`: открыть базу лаунчера по папке пользователя (нет файла → ошибка), найти
  плейсет (активный, по имени, по id), определить язык анализа, загрузить плейсет с прогрессом,
  проиндексировать ваниль (с проверкой папки игры), путь к логу и его чтение, проверка
  «плейсет изменился». CLI переходит на него.
- Пункты бэклога «До плана 2»: проверка лаунчера fail-closed (своего процесса нет в списке →
  отдельная ошибка «список процессов недоступен»); бэкап через `VACUUM INTO` в заведомо новый
  файл; текст `OrderMismatch` без команды CLI; `load_mod` без `Result`; JSON CLI — с именами модов,
  и у `sort` / `calibrate` — с предупреждениями индекса.
- Правила как зависимости для пометок (§4.4); пары модов; текст строки локализации по файлу и
  ключу — для показа сторон конфликта; имя будущей копии плейсета без записи (для диалога §4.8.3).
- Память и скорость (Q25): пути файлов, база и язык общие, а не копия в каждом определении;
  транзитивные зависимости считаются один раз на анализ; определения сортируются внутри групп, а
  не все сразу. Замер пиковой памяти и времени до и после на реальном плейсете владельца (игра и
  моды Workshop на его Mac есть), с ванилью и без; эталоны `conflicts --json`, `sort --json`,
  `calibrate --json` снимаются прямо перед оптимизацией и после неё совпадают байт в байт. Цель —
  пиковая память минимум вдвое меньше; не достигнута — числа в бэклог, дальше решает владелец.
  Оптимизация идёт до экранов: приложение строится уже на итоговых типах ядра.

## 5. Ошибки и крайние случаи

- Папка мода отсутствует (подписка не скачана) → «не найден на диске», из анализа исключён.
- Нет базы лаунчера или в ней нет нужных столбцов → понятная ошибка, ничего не пишем.
- Битая кодировка, BOM, кривой синтаксис → предупреждение на файл, анализ продолжается.
- Пути, отличающиеся регистром → один файл на Windows/macOS, разные на Linux.
- Два мода с одинаковым `name` → «неоднозначная зависимость».
- Лог `database_conflicts.log` оборван (последняя строка без закрывающей кавычки) или
  записан для другого набора модов (сверка с `dlc_load.json`) → предупреждение в `calibrate`.
- Вывод детерминирован: одинаковый вход → одинаковый порядок строк отчёта.

## 6. Проверка

- Модульные тесты на мини-модах и на тестовой базе лаунчера, созданной из реальной схемы
  (`crates/ck3h-core/fixtures/launcher_schema.sql`, снятой через `.schema --nosys`).
- `ck3h calibrate` сверяет прогноз с `database_conflicts.log` в обе стороны:
  совпало / разошлось (другой файл-победитель) / в логе есть, у нас нет (по базам) /
  в логе есть, а мы видим только одно определение (по базам — значит, мы что-то не нашли) /
  мы предсказали переопределение, а в логе его нет. «Совпало» и «разошлось» считаются только
  там, где мы видим два и более определения. Перед сверкой проверяет, что лог относится к
  этому плейсету (`dlc_load.json`) и не оборван. Цель на реальном плейсете — все расхождения
  разобраны и объяснены до релиза. Срез реального лога — фикстура тестов.
- Ручная проверка применения: копия реальной базы → `sort --apply` → запуск лаунчера →
  новый плейсет виден и запускается.

## 7. Открытые вопросы (проверяются на реальном плейсете)

1. Правило «первое определение локализации побеждает» взято из исходников tiger; справочник
   по моддингу говорит обратное. Решает ручная проверка в игре.
2. Порядок чтения путей с разным регистром: принят побайтовый с учётом регистра (одно
   подтверждение из реального лога); перепроверить на свежем логе и на Windows.
3. Полнота списков: корни `gfx/`-баз, базы без объектного анализа и базы-«контейнеры».
4. Принимает ли лаунчер вставленный плейсет и как с ним обходится синхронизация аккаунта.
5. Имена процесса лаунчера на Windows/macOS/Linux.
6. Объявляют ли моды-переводы зависимость от основного мода. *Ответ реального плейсета:* нет —
   1098 из 1161 подозрительных строк локализации дал один перевод. Решение Q20: пары модов и одно
   правило «оригинал раньше перевода» делают пару задуманной; отдельной метки «перевод» в v1 нет.
